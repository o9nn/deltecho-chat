# Tentative Predictive Crystal: an evidence-limited DTE–Live2D cycle

**Author:** Manus AI

**Status:** implementation specification, 5 October 2026

The existing scientific engine stores a bidirectional concept graph, but its predictive-crystal routine tries to recover graph nodes from formatted insight prose rather than using that graph. The autonomy lifecycle listens for crystal events but never calls the routine; its current reaction is a timed local ESN-avatar flag rather than the mounted Live2D manager. The Live2D conductor already supports a short crystal timeline, but its crystal-only overlay reports `active: false`, so the manager neither composites it per frame nor samples its actual output. These are implementation observations, not claims of scientific discovery. [1] [2] [3]

> **Definition:** A predictive crystal is an _untested, internal graph-link conjecture_, not a verified scientific finding, Bayesian posterior, DAO vote, identity update, or permission to modify the ESN. A normalized visual `confidence` value is a bounded structural support score, **not a calibrated probability of truth**.

| Boundary          | Required behavior                                                                                                                                                                                                                                                                                                               | Falsifiable test                                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Engine            | Find A–C–B paths from stored typed concept IDs, reject direct A–B edges, and bound graph work and output. Never extract edges from insight text.                                                                                                                                                                                | A small graph with two supported edges produces a conjecture; a closed triangle or disconnected graph does not.                   |
| Autonomy          | Run graph discovery only after a scheduled scientific _stimulus_ contributes a new concept. Repeated scans must not re-emit the same unordered candidate pair.                                                                                                                                                                  | Reflection cadence produces at most one bounded cue per inquiry; repeated invocation does not replay the same pair.               |
| Governance        | Crystal events remain proposal-only observations. No self-modification, reservoir spectral-radius mutation, canonical acceptance, or DAO vote follows from a tentative crystal.                                                                                                                                                 | Event/ledger tests prove accepted identity head and parameter state do not change.                                                |
| Backend transport | Send only `id`, creation time, normalized support, and bounded avatar-effect scalars in the existing Entelechy visual snapshot. Omit user text and concept names. Retain the signal for no more than 2,500 ms; copy on return.                                                                                                  | Repeated reads are stable until expiry, then omit the cue; mutations to returned objects do not alter stored state.               |
| Desktop bridge    | The Electron main frame may request only `cognitive:get_state` from the existing local orchestrator socket, then forward only its scientific visual subobject. Cap payload size and timeout; return `null` if the daemon is absent, errors, or replies with the wrong request ID. Browser/Tauri targets have no implied daemon. | Real socket tests verify read-only framing, field minimization, spoof/oversize rejection, and unavailable-daemon abstention.      |
| Frontend          | Poll the optional desktop getter without overlapping requests, pause when hidden, and ignore late results after unmount. Forward only an Entelechy-origin, non-expired cue; local sentiment cannot synthesize one. Include cue identity in the avatar update signature.                                                         | A genuine daemon signal reaches the mounted Live2D prop; disappearance revokes it, while local/unmarked cues are ignored.         |
| Cubism            | Reuse the existing renderer ticker and per-avatar conductor. Crystal-only motion is subtle eye focus and brow asymmetry, **without the eureka halo or insight smile**; cap parameters and include the cue in predicted-versus-rendered sampling. No new timer, context, or ticker listener.                                     | A crystal-only ticker pass writes bounded eye/brow values, no halo/smile, then decays; `dispose()` removes the existing listener. |

The feature changes the scientific-engine → autonomy → Entelechy snapshot → **optional Electron main-frame socket broker** → mounted avatar → calibrated Cubism/self-model path. The installed app does not start the orchestrator daemon as part of this feature; when the daemon is not running, it remains on local visual observations rather than fabricating scientific state. The public static GitHub Pages illustration must not claim to run this feature. Runtime appearance is verified only when an authenticated live app is actually observed; the code-level integration and browser E2E suites are distinct evidence. [2] [3] [4]
